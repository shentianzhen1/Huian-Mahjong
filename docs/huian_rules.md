# 惠安二人麻将：已确认规则范围

本文件是面向开发的中文摘要。规则状态和证据冲突仍以根目录
[`RULE_STATUS.md`](../RULE_STATUS.md) 为准。玩家于 2026-09-14 确认的
规则优先于旧代码、legacy 注释和外部泉州玩法资料。真实目标房画面优先于玩家反馈；不同胡法的证据不得相互套用。

## 金牌与胡牌限制

- 目标房勾选“单金不平胡”：恰好1张金不能点炮平胡，但标准结构成立时可以自摸胡。
- 恰好持有2张金时只能自摸胡，不能胡对手打出的任何牌。
- 对手直接打出的当前金牌本身也不能吃、碰、杠或胡。
- 普通胡牌判断与游金判断是两个独立分支，不能用一个布尔 `can_hu()` 同时代替。
- b3892b34 真实回放确认：万、筒、条三门同时存在，持1金仍可普通自摸；目标房普通自摸不要求“必须缺一门”。

实现时先识别胡牌来源（自摸或点炮），再应用金牌数量限制，之后分别进入
普通标准结构判断或游金状态判断。三金倒继续作为独立特殊分支。

## 补花的系统交互与录像识别

玩家确认：补花由小程序自动派发，界面没有明显的逐张派发动画。Environment
应把补花建模为系统自动事件，不生成等待玩家确认或点击的动作。

Vision/Recorder 后续不得以“检测到补花动画”作为流程成立条件，而应比较补花前后
的稳定状态：手牌数量、花牌数量、牌墙剩余数量，以及是否进入开金阶段。录像中
没有明显动画不代表没有执行补花。这条确认只定义 UI/录像层的观测方式，不改变
既有的牌尾补牌来源、庄家到闲家的轮次或连续花处理规则。

## 三金倒与三金游选择

已确认：

- `can_sanjindao = hand_gold_count >= 3`，不要求先满足普通标准胡结构。
- 三金倒是可选动作，不是检测到3张金就自动结束本局。
- 玩家可以立即声明三金倒，也可以继续走游金路线，等待“三金游”。
- 三金游采用与二金游相同的触发流程；三张金并不把玩家限制在三金倒一条路径上。
- 三金游与三游是同一种状态，代码统一使用 `TRIPLE_YOU`；`SANJIN_YOU` 只作为同值别名。
- 三金倒是不同的独立结果，确认为×3；三游确认为×16。
- AI 必须比较“立即三金倒”和“继续做三金游”，不能固定选择其中一个。

“三金游”和“三游”是同一状态的两个名称，不建立两套状态机。“与二金游流程
相同”这一关系已确认，但二金游/三游的完整可执行状态步骤还没有被逐项定义；
两者倍率已经确认；非花底数、付款、完整结算和声明窗口仍为 UNKNOWN。
Rules 应先暴露 `DECLARE_SANJINDAO` 与 `CONTINUE_PLAY` 两个合法动作；三金游细节
没有证据时，进入相关状态必须安全停止。

## 杠后摸牌与杠胡

已确认：

- 明杠、暗杠、补杠完成后都从牌尾摸牌。
- 杠后摸牌复用正常摸牌流程；若摸到花，继续进入已有补花流程。
- 动作只需额外记录摸牌来源为 `wall_tail`，无需另建一套复杂补牌流程。
- 杠牌者在明杠、暗杠或补杠后的这次尾摸中胡牌，全部统一归类为杠胡。

实现边界：杠胡是“完成杠的玩家在随后的牌尾摸牌后胡”。其他玩家在杠声明
期间胡牌属于抢杠胡，是另一条响应路径。当前按用户本轮实现要求接入补杠专用
响应窗口；明杠/暗杠抢杠范围、抢杠实际房间交互证据及计分仍为 UNKNOWN。
杠胡自身的番数、倍率和叠加也尚未确认。

## 补杠专用响应：本轮实现要求

本节记录已实现的工程流程，不将实现或测试当作真实录像证据。66fe863f 回放
确认碰后补杠这一动作，没有展示抢杠尝试或拒绝分支。

- 已有非金牌 PENG 且手中有同牌第4张时，可选择 `ADD_KONG`；金牌禁止补杠。
- 声明进入 `ROB_KONG_WINDOW`，原PENG和第4张手牌均先保留，`pending_kong`只作逻辑引用。
- 只有该补杠窗口提供符合 Rules 资格的 `ROB_KONG_HU` 或 `PASS`。抢胡记录赢家与来源，原碰不升级、不摸补牌。
- PASS 后第4张只转移一次，形成 `ADDED_GANG`；随后必须从 `wall_tail` 摸牌并复用已有补花流程。
- `enable_added_kong`默认True，False禁用候选；Simulator的广义 `enable_rob_kong` 仍为False/未支持，不表示明杠、暗杠也可抢。
- 抢胡成功停在 `ROB_KONG_SCORING_UNKNOWN`；尾摸后声明胡停在 `GANG_HU_SCORING_UNKNOWN`；补杠尾摸不胡停在 `ADD_KONG_SCORING_UNKNOWN`。均不套普通平胡/自摸奖励。
- 含补杠的补花不跨16张边界；边界结算继续UNKNOWN，不默认零杠费流局。

## 不采用的复杂番型

目标规则不设置以下独立番型或额外奖励：

- 门清
- 碰碰胡
- 清一色
- 混一色
- 其他类似复杂组合番型

“不计番”不表示这些牌张组合非法。例如一副全部由刻子构成、但同时满足
标准胡牌结构和金牌限制的手牌，仍可按普通胡处理，只是不获得“碰碰胡”奖励。

## 吃牌多方案选择

已确认规则及系统交互：对手打出一张牌，而我方同时存在多个合法吃牌组合时，
小程序会弹出吃牌方案选择界面，由玩家选择具体吃法。系统不会自动选择，也
不能把一个没有组合信息的“吃”动作直接执行。

例如对手打出5万，我方同时持有对应牌时，应提供：

- 3万、4万：组成3万4万5万
- 4万、6万：组成4万5万6万
- 6万、7万：组成5万6万7万

代码接口要求：

- Rules 的 `chi_options(discard, hand)` 返回所有合法顺子列表，不只返回布尔值。
- 每个候选生成一个携带完整三张牌组合的独立 `CHI` 动作。
- Environment 只执行玩家或 AI 明确选中的组合，并按该组合移牌、生成副露。
- AI 把不同吃法当作不同动作，分别计算后续弃牌、进张和风险。
- Vision/Executor 后续必须识别方案弹窗并选择与 `CHI.tiles` 完全一致的选项；方案映射不确定时停止，不允许默认点击第一个。

当前 `HuianRules.meld_options()` 和 Environment 已使用具体组合动作表达这一规则；
弹窗视觉识别与点击尚未接入。吃牌执行完成后，当前玩家必须立即进入弃牌阶段，
与碰后流程相同；中间不摸牌。现有 Environment 已实现该状态转移。

## 游金计分项

目标房已确认：

- 游金 ×4。
- 双游 ×8（游戏内惠安规则页高可信；录像可见双游中间状态，但尚缺停在双游的目标房×8终局结算）。
- 三游/三金游 ×16。
- **庄家游金不额外×2。** room541913第5局庄家游金：庄底15、金2+花2=4番，实际`(15+4)×4=76`；与既有庄家三游`(35+3)×16=608`一致。
- 花牌每张计1番，先进入赢家番数，再与当前庄底一起乘胡法倍率；真实三游结算已验证该顺序。

现有游金计分项接口使用 `(当前庄家底 + 赢家番数) × 游金倍率`；庄家倍率固定为1，已由庄家游金+76和庄家三游+608直接验证。
真实三游报告中，庄底35、金牌1番、两张花2番：`(35 + 3) ×16 = 608`。
这推翻了此前“花牌最后单独加、不乘游番”的说法。`YoujinScoreTerms` 接收已审计的
赢家番数，不自动猜多金、花组或其他未确认番项；付款、结算后庄位和完整触发时序仍为 UNKNOWN。

这些确认解决了权限矩阵的一部分，但没有补全游金下具体可胡来源、双游下
除自摸外是否还有其他胡牌窗口，以及各状态的完整响应时序。未确认部分继续
保持 UNKNOWN。

## 分层实现要求

- Rules：标准胡结构、金牌数量、自摸/点炮来源、可选三金倒、统一杠胡分类、八花游，以及独立的游金链资格和分级对手权限。
- Rules：吃牌资格返回全部合法顺子组合，不使用单一 `can_chi: bool` 代替候选列表。
- Scoring：游金×4、三游×16为目标房直接结算确认；双游×8为高可信待终局实证。赢家番数（包含每花1番、每金1番）先与当前庄底相加，再乘胡法倍率；庄家不另乘×2。只组合已保留项目，八花游特殊倍率未确认时不得猜测。
- AI：重点评估普通胡、自摸价值、三金倒、三游/三金游、游金路径与风险；三金倒可用时比较立即声明和继续做三游，不为门清、碰碰胡、清一色、混一色等已排除番型改变策略。
- Environment/Simulator：执行吃牌时必须携带选定组合；三类杠完成后以 `wall_tail` 来源复用正常摸牌流程。在 Rules 返回明确资格前保持 UNKNOWN 安全停止，不自行推断特殊胡触发或倍率。

当前 Rules 已用 `HuContext` 显式携带自摸、点炮、杠后尾摸、胡牌张和杠种，
并实现1金/2金来源限制、弃金不可胡及三金倒纯资格决策。Environment 已把新事件
统一写成 `wall_head` / `wall_tail`，杠后尾摸还会记录 `kong_kind` 和 `drawn_tile`。
三金倒的牌局声明窗口、`TRIPLE_YOU` 状态机、非花底数/付款、杠胡倍率和自动结算仍保持 UNKNOWN，尚未
因为基础接口完成而被提前启用。
